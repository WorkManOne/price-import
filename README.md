# price-import — «Умный импорт прайса»

Задание 17. Сервис импорта каталога товаров из CSV.

Перед применением строится отчет: какие строки новые, какие изменят товар (и что именно), какие
без изменений, какие некорректные (и почему). Применяется только подтвержденный отчет, одной транзакцией,
и только если каталог с момента построения отчета не поменялся. Все изменения пишутся в историю,
примененный импорт можно откатить.

- Go 1.25, PostgreSQL 16, HTTP API (`net/http`), драйвер `pgx/v5`, `golang.org/x/text` для cp1251
- консольный клиент `pricectl` для демонстрации
- OpenAPI: [`api/openapi.yaml`](api/openapi.yaml), Swagger UI на `/docs`

---

## 2. Как пользоваться

```text
1. POST /api/v1/imports            файл -> отчет (импорт в статусе analyzed). каталог НЕ меняется
2. GET  /api/v1/imports/{id}       сводка + reportHash
   GET  /api/v1/imports/{id}/items?kind=changed   строки отчета
3. POST /api/v1/imports/{id}/apply {"reportHash": "...", "skipInvalid": true}
```

То же через клиент (внутри контейнера он уже есть, примеры лежат в `/app/examples`):

```bash

docker compose exec app pricectl apply 2 -skip-invalid
```

## 3. Архитектура

```text
 pricectl / curl / Swagger
          │ HTTP
          ▼
 internal/httpapi    ручки, коды ошибок, DTO (цены строкой)
          │
 internal/catalog    импорт: анализ, применение, отмена, откат, ручная правка,

          ├── internal/pricecsv   разбор CSV: кодировка, разделитель, заголовки, проверка полей
          ├── internal/diff       сравнение строк с каталогом -> отчет + reportHash (без базы)
```

`pricecsv`, `diff` и `money` не знают про базу и покрыты обычными юнит-тестами.

## 4. Формат CSV

| колонка   | заголовки (регистр не важен)                    | обязательна |
|-----------|-------------------------------------------------|-------------|
| sku       | sku, артикул, article, code, код                | да          |
| name      | name, наименование, название, title, товар      | для новых   |
| category  | category, категория, группа                     | нет         |
| price     | price, цена                                     | для новых   |
| stock     | stock, остаток, qty, quantity, количество, кол-во | нет       |

- Хвост заголовка после запятой или скобки отбрасывается: `Цена, руб.` → `цена`, `Остаток (шт)` → `остаток`.
- Незнакомые колонки игнорируются, в отчете предупреждение.
- **Колонки, которых нет в файле, не меняются.** Файл `sku;цена` меняет только цены.
- Разделитель `,` `;` или таб — угадывается по заголовку (можно задать `delimiter=`).
- Кодировка UTF-8 (с BOM или без) или Windows-1251. `encoding=auto`: если байты — валидный UTF-8,
  значит UTF-8, иначе cp1251.
- Пустые строки и строки из одних разделителей (`;;;;`) пропускаются.
- Номер строки в отчете — номер строки в файле (заголовок = 1), с учетом многострочных значений в кавычках.
- Лимиты: файл 20 МБ (`MAX_UPLOAD_MB`), 100 000 строк (`MAX_ROWS`).

### Правила проверки строки

| поле     | правило |
|----------|---------|
| sku      | не пустой, до 64 символов, буквы/цифры/`- _ . /`, без пробелов. **Приводится к верхнему регистру**: `ab-1` и `AB-1` — один товар |
| name     | если колонка есть — не пустое, до 255 символов, без управляющих символов. Повторные пробелы схлопываются (`Чайник  синий` = `Чайник синий`, иначе это было бы «изменение») |
| category | может быть пустой (= без категории), до 255 символов |
| price    | `1299`, `1299.9`, `1 299,90`, `1299.900`. Не больше 2 знаков после запятой (лишние нули можно), не отрицательная, до 1 млрд. `1,299.90` — ошибка (непонятно, что имелось в виду). Хранится в копейках, float нигде нет |
| stock    | целое `>= 0`, до 1 млрд |

Все ошибки строки выводятся сразу, а не по одной. Строка с ошибкой не применяется никогда.

Особые случаи:

- **Дубль артикула в файле** — некорректны *все* его строки: какая из них правильная, сервис не знает.
- **Кавычка посреди значения** (`Монитор 27"` без кавычек вокруг) — эта строка некорректна, но файл
  читается дальше, а в отчете виден ее артикул.
- **Незакрытая кавычка** — дальше файл не разобрать, файл отклоняется целиком с номером строки.
- **Новый товар без названия или цены** (например, в файле только `sku,price`) — некорректная строка.

Файл **отклоняется целиком** (HTTP 422, импорт сохраняется со статусом `rejected`): пустой файл,
нет колонки артикула, нет ни одной колонки кроме артикула, колонка указана дважды, незакрытая кавычка,
неизвестная кодировка, больше `MAX_ROWS` строк, full-импорт без единой корректной строки.

### Предупреждения (не блокируют)

- цена изменилась в 3 и более раз (потерянный ноль, копейки вместо рублей);
- нулевая цена;
- проигнорированы незнакомые колонки;
- full-импорт снимает с продажи больше 30% активного каталога;
- этот же файл (по sha256) уже применялся.

## 5. Отчет

Каждая строка файла попадает ровно в одну группу:

| kind        | что значит |
|-------------|------------|
| `new`       | товара с таким артикулом нет — будет создан |
| `changed`   | товар есть, поменяется хотя бы одно поле (в отчете: поле, было → стало) |
| `unchanged` | товар есть, все значения совпадают |
| `invalid`   | строка некорректна (список причин + исходные значения) |
| `missing`   | только full-режим: активный товар, которого нет в файле, — будет снят с продажи |

Режимы:

- `partial` (по умолчанию) — меняются только товары из файла.
- `full` — файл описывает весь каталог: активные товары, которых в нем нет, получают `active=false`.
  Физически ничего не удаляется. Товар, чья строка в файле некорректна, **не** снимается
  (иначе опечатка в цене сняла бы товар с продажи). Строки без артикула здесь, понятно, не помогут.
- Если товар был снят с продажи, а теперь есть в файле, он снова становится активным (это изменение `active`).

Отчет сохраняется в базе целиком (`import_items`), вместе с версией каждого товара на момент анализа.
Применяется ровно сохраненный отчет, а не пересчитанный заново.

## 6. Статусы импорта

```text
               ┌─ apply (каталог не менялся) ─> applied ── revert ─> reverted
upload ─> analyzed ─ apply (каталог поменялся) ─> stale
   │           └─ cancel ─> canceled
   └─ файл не разобран ─> rejected
```

- `stale`, `canceled`, `rejected`, `reverted` — конечные. Протухший импорт не «оживает»:
  нужно загрузить файл заново и посмотреть новый отчет.
- Повторный `apply` для `applied` → 200 `alreadyApplied: true`, ничего не делает.
- Повторный `cancel` для `canceled` и `revert` для `reverted` — тоже без ошибки.
- Остальные переходы → 409 `bad_status`.

## 7. Подтверждение

`POST /imports/{id}/apply` требует:

- `reportHash` — sha256 от содержимого отчета (что, с какими значениями и от какой версии товара
  будет применено). Клиент берет его из отчета, который показал человеку. Не совпал → 409
  `report_hash_mismatch`. Так нельзя «подтвердить» импорт не глядя или по другому отчету.
- `skipInvalid: true`, если в отчете есть некорректные строки. Иначе 422 `invalid_rows_not_confirmed`:
  пропуск строк — это осознанное решение, а не тихое поведение по умолчанию.

## 8. Согласованность при применении

Главное: **импорт применяется целиком или не применяется вообще, и только к тому каталогу,
по которому построен отчет.**

### Что делает apply (одна транзакция)

```text
BEGIN
  SELECT pg_advisory_xact_lock(LockCatalog)        -- exclusive: один пишущий в каталог
  SELECT ... FROM imports WHERE id=$1 FOR UPDATE    -- статус, hash, skipInvalid
  проверка: каждый товар из отчета (new/changed/unchanged/missing)
     new        -> товара все еще нет
     остальные  -> products.version == base_version из отчета
     full-режим -> нет активных товаров, которых не было в отчете
  если не совпало -> imports.status = 'stale' + событие с конфликтами, COMMIT, 409 import_stale
  INSERT новых (unnest, пачкой)
  UPDATE измененных/снимаемых ... WHERE version = base_version (пачкой), проверка числа строк
  INSERT в product_history (пачкой)
  imports.status = 'applied', событие
COMMIT
```

Почему так:

- **Версии товаров** (`products.version`, +1 на любое изменение). Любое изменение товара после
  анализа (ручная правка, другой импорт, откат) делает отчет устаревшим *для этого товара*.
  Проверяются в том числе `unchanged`: если в файле цена 100, а пока отчет ждал, ее руками поставили
  120, после «применения» осталось бы 120, а человек подтверждал другое.
- Проверка по товарам, а не по каталогу целиком: два импорта по разным товарам из одного снимка
  применяются оба. Два импорта по одному товару — успешен первый, второй `stale`.
- **Advisory lock в PostgreSQL**, а не `sync.Mutex`: работает между несколькими экземплярами сервиса.
  Пишущие операции: `apply` и `revert` берут exclusive, ручная правка — shared (правки идут
  параллельно друг с другом, но не во время применения). Без него ручная правка могла бы пройти
  между проверкой версий и UPDATE; `WHERE version = base_version` такое тоже поймал бы и откатил
  транзакцию, но с ошибкой 500 вместо понятного 409, а лок делает это корректным `stale`.
- Анализ читает каталог в `REPEATABLE READ` — один согласованный снимок даже во время чужого apply.
- Апдейты пачками через `unnest`: 100 000 строк — одна команда, а не 100 000 запросов.
- Если клиент отвалился посреди `apply`, транзакция все равно доводится до конца
  (`context.WithoutCancel`), иначе он не узнал бы результат. Повторный apply ответит `alreadyApplied`.
- Если процесс убить посреди применения — postgres откатит транзакцию: каталог, статус и история
  останутся как до apply (проверялось `docker compose kill -s SIGKILL app` во время apply на 100k строк).

### Несколько экземпляров

Все гарантии держит PostgreSQL (транзакция, advisory lock, `FOR UPDATE`, версии), в памяти процесса
состояния нет. Миграции при старте под `pg_advisory_lock`, так что одновременный старт двух экземпляров
не ломает схему.

Проверка: `./scripts/two_instances.sh` поднимает второй экземпляр сервиса, строит 10 импортов одного
товара из одного снимка и одновременно применяет их через оба экземпляра по очереди:

```text
применено: 1, отклонено как stale: 9 (ждем 1 и 9)
```

### Ручная правка товара

`PATCH /api/v1/products/{sku}` с `version` — оптимистичная блокировка: правка по устаревшей версии →
409 `version_conflict` с актуальным товаром. Нужна, чтобы показать, как ручные изменения делают отчеты
устаревшими, и чтобы правки не терялись.

## 9. История

- `import_events` — журнал импорта: `analyzed`, `rejected`, `applied`, `stale` (со списком конфликтов),
  `canceled`, `reverted`. `GET /imports/{id}/events`
- `product_history` — каждое изменение товара: источник (`import` / `manual` / `revert`), номер импорта,
  действие (`created` / `updated` / `deactivated` / `deleted`), состояние до и после, версия после.
  Пишется **в той же транзакции**, что и изменение, — изменение без записи в истории невозможно.
  `GET /products/{sku}/history`, `GET /imports/{id}/changes`
- Сами импорты и их отчеты не удаляются.

### Откат

`POST /imports/{id}/revert` — по истории импорта возвращает товарам старые значения, созданные
импортом товары удаляет (история о них остается). Можно, только если **ни один** затронутый товар
не менялся после импорта (`version == version_after`), иначе 409 `revert_conflict` со списком —
сервис не решает за человека, чья правка важнее. Все или ничего, те же блокировки, что у apply.

## 10. Структура БД

```text
products         sku PK, name, category, price_kopecks, stock, active, version, created_at, updated_at
imports          id, status, mode, filename, file_sha256, file_size, encoding, delimiter, columns,
                 ignored_columns, счетчики по видам, warnings, report_hash, error,
                 created_at, applied_at, canceled_at, reverted_at
import_items     (import_id, seq) PK, line, kind, sku, base_version, old_state, new_state,
                 changes, errors, warnings, raw            -- отчет
import_events    id, import_id, type, message, details, created_at
product_history  id, sku, import_id, source, action, old_state, new_state, version_after, created_at
```

Индексы: `import_items (import_id, kind, seq)` — страницы отчета по виду; `product_history (sku, id)` и
`(import_id, id)` — история товара и изменения импорта; `imports (file_sha256)` — повторный файл;
`products (category)`. CHECK-ограничения на статусы, виды, неотрицательные цену и остаток.
Миграции — `internal/db/migrations`, применяются при старте.

## 11. API

| метод | путь | что |
|-------|------|-----|

## 12. Тесты

`go test -race ./...` (в докере: `docker compose --profile test run --rm --build tests`).
Тесты с базой создают себе отдельную схему postgres, так что пакеты не мешают друг другу.

- `money` — форматы цен, точность, переполнение, round-trip
- `pricecsv` — разделители, BOM, cp1251, синонимы заголовков, ошибки заголовка, номера строк
  с многострочными значениями, битые кавычки, лимит строк, проверки каждого поля, дубли
- `diff` — классификация, частичные колонки, новые без имени/цены, реактивация, full-режим
  (битые строки не снимаются), предупреждения, стабильность и чувствительность `reportHash`
- `catalog` (на postgres):
  - анализ не меняет каталог, отклоненный файл сохраняется
  - apply: создание/обновление, `unchanged` не трогает версию, неверный hash, битые строки без
    подтверждения, идемпотентность
  - **stale**: ручная правка товара из отчета, правка `unchanged`-товара, новый товар уже появился,
    два импорта из одного снимка, новый активный товар в full-режиме — во всех случаях каталог
    не меняется вообще (проверяется и незатронутый конфликтом товар)
  - отмена, откат, конфликт отката, повторная загрузка после отката
  - история и события
  - **конкурентные**: 30 одновременных apply одного импорта → ровно 1 применение; 10 импортов одного
    товара из одного снимка → 1 успешен, 9 stale; 10 импортов разных товаров → все успешны;
    ручная правка против apply (20 раундов) → всегда ровно один победитель; apply против cancel →
    ровно один победитель; после гонок число записей в истории = число версий
  - импорт 20 000 строк
- `httpapi` — коды ответов и ошибок, multipart/raw, лимит размера, apply/stale/revert через HTTP,
  ручная правка с ценой числом, **все ручки описаны в openapi** (тест сверяет `server.go` со спекой)

## 13. Замеры

MacBook (Apple Silicon), Docker Desktop, postgres в контейнере, время через `pricectl`
(с учетом `docker exec` и HTTP). Сгенерированный прайс: `pricectl gen -n 100000` (~5 МБ).

| сценарий (100 000 строк) | загрузка + разбор + отчет | применение |

| full-режим по каталогу 100k (изменено 35 584, снято 13) | 2.2 с | 1.6 с |

## 14. Что не делали

- авторизацию и пользователей (история пишет источник, но не автора);
- асинхронный анализ: файл до 20 МБ / 100k строк разбирается синхронно за пару секунд,
  очередь заданий тут усложнила бы больше, чем дала;
- XLSX — только CSV;
- несколько валют — цены в рублях;
- удаление товаров через импорт — только снятие с продажи (`active=false`);
- автоопределение кодировок кроме UTF-8/cp1251. Файл, где UTF-8 перемешан с cp1251, целиком
  прочитается как cp1251 (в отчете будут кракозябры — видно сразу, ничего не применится без подтверждения).
